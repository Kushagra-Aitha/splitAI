Split · System design

A real bank underneath, a time-series ledger at the core.

Split runs on its own bank, Capital Two, built on Capital One's Nessie API. Every account, purchase, deposit and transfer is a real Nessie operation. Every dollar lands in Tiger Data, which also does the locking, deduplication and request tracking that keep money correct. Gemini handles language and voice, and never touches money.

System architecture

Two apps, one origin, one database

Users reach two front ends: Split, and the Capital Two bank. Both share one session and one HTTPS origin on Vultr. Behind the security gate, Split's features sit on a banking layer that works with any bank. Capital Two has its own payment engine and worker. Every module writes to Tiger through one connection pool.

Nessie · Capital Two

A bank built on Nessie, used by every money feature in Split: opening accounts, buying, depositing, transferring, settling and recovering.

Nessie integration map

Every user action, the Nessie call it makes, and where it is stored

Split uses 13 Nessie operations. Each one has a single owner in the server and a fixed place in Tiger, so every dollar can be traced from the button press to the bank and back.

Opening accounts is repeat-safe

Provisioning stores the Nessie customer ID first, then reuses any account already tagged Split · <user> before creating one. A crash between Nessie's reply and our write never opens a second account.

Opening is not sharing

Accounts start unlinked. Only the Connect screen's Allow sets linked_at; only linked accounts sync, count in Overview, or move money.

Built for any bank

Nessie is one provider behind an adapter. Every transaction becomes integer cents, a fixed kind, a direction and a status, so adding a bank means adding one adapter.

Capital Two payment engine

A payment is saved before it is sent, and never sent twice

Nessie has no idempotency key for creates. So every Capital Two payment is a row in capital_operations before any bank call, carries the user's request key, and tags its Nessie description with the operation ID. One request wins the right to send. If the bank's answer is lost, the worker finds the payment by that tag instead of sending it again.

Settle up

Claim in Tiger, send to Nessie once, reconcile on the next sync

Paying a friend back is a real Nessie transfer, split into three steps so a crash or timeout at any point leaves the books correct. Money is held before the call, the call is made once, and the bank's own records decide whether it counts as paid.

Tiger Data

Tiger is both the time-series store for bank activity and the concurrency control for every money operation.

Sync into Tiger

From Nessie's raw activity to a deduplicated hypertable

The provider read happens outside the database. The write is one Tiger transaction per account, under the same row lock that funds and settlements use, so a balance refresh can never interleave with a hold.

Hypertable · time_bucket

A question about this month reads this month's chunks

bank_transactions is partitioned by occurred_at. A November query scans November's chunks however long the history grows. The Overview chart is one time_bucket query joined to a generate_series, so days with no activity come back as zero instead of a gap.

Tiger as the coordination layer

Two processes, one payment, one send

Split can run several API processes plus the Capital Two worker. They do not coordinate in memory. Tiger decides who goes first, using row locks, conditional updates, unique keys and advisory locks.

Row locks on money

SELECT … FOR UPDATE on the checking account serializes funds holds, goal deposits, settlement claims, bank sync and provisioning.

Unique keys as idempotency

(user_id, request_key), (account_id, provider_key), (schedule_id, occurrence) and unique provider_reference turn retries into reads.

Advisory locks

pg_advisory_xact_lock per merchant name means two tabs or two processes create a Nessie merchant at most once.

Partial indexes as work queues

The worker reads unresolved operations and due schedules through indexes limited to status IN ('queued', …) and status = 'active'.

Snapshot reads

Insights run in REPEATABLE READ READ ONLY, so a sync landing mid-request cannot change half of the numbers.

Constraints in the schema

CHECK on every amount and status, hold_cents ≤ amount_cents, payers must be group members, and a bank purchase can back at most one confirmed expense.

Data model

Time-series and relational data, joined in plain SQL

The hypertable sits at the center of the ledger. An expense points at the exact bank purchase it split, a settlement is matched to the Nessie transfer that paid it, and a Capital Two payment is found again by its provider reference after a lost response.

End to end

From a pizza to a posted transfer

Maya buys pizza at Capital Two, asks Split by voice to split it with Sam and Priya, and Sam pays her back. Every arrow is a real call. The two blue arrows are the only places money is approved, and both come from a person.

AI security

Hacking the model gets you a draft, not a payment

Split assumes Gemini can be tricked and chat messages can be hostile. Actions need a person, chat is scored on our own server, and numbers come from SQL.
