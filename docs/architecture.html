System architecture

One origin on Vultr, four providers, one database

The browser only ever talks to one HTTPS origin. Nginx terminates TLS and forwards to a Node process bound to localhost; every request passes the session, Origin and CSRF checks before any module runs. Provider keys stay on the server.

Single origin

The built front end and /api come from the same Node process, so cookies are SameSite=Strict and there is no CORS surface.

One runtime dependency

The server depends only on pg. HTTP, sessions, rate limits and provider clients use Node's standard library.

Production defaults

An HTTPS APP_ORIGIN turns on __Host- cookies, Secure and HSTS. The app ignores forwarded headers and stays private behind Nginx.

Tiger Data · TimescaleDB

Bank activity is a time series, so it lives in a hypertable

bank_transactions is partitioned by occurred_at. A query for this month only scans this month's chunks, however long the history grows. The Overview chart is one time_bucket query joined to a generate_series, so days with no activity come back as zero instead of a gap.

Dedupe without timestamps

A hypertable's unique keys must include occurred_at. The bank's transaction ID lives in bank_import_keys, inserted with the row in one transaction, so a resync never doubles a dollar.

Money under a lock

Spendable = available − goal reservations − settlement holds, computed under SELECT … FOR UPDATE. Sync, goals and settlements take the same lock.

Snapshot reads

Insights run in REPEATABLE READ READ ONLY, so a sync landing mid-request cannot change half the numbers on the page.

Checked, not trusted

banking:overview-check recomputes every bucket from raw rows; db:verify rebuilds a throwaway schema and confirms the hypertable.

Data model

Time-series and relational data, joined in plain SQL

The hypertable sits at the center of the ledger. An expense points at the exact bank purchase it split, a settlement is matched to the Nessie transfer that paid it, and a Capital Two payment is found again by its provider reference after a lost response.

AI security

Hacking the model gets you a draft, not a payment

Split assumes Gemini can be tricked and chat messages can be hostile. Three paths show where text can and cannot go: actions need a person, chat is scored on our own server, and numbers come from SQL.

Identity from the session

Payer, group and members are resolved against the signed-in user. Names from the model are hints, never identities.

Guard is a second layer

Rules for instruction override, outside payment and credential requests explain each flag. A miss still cannot move money.

Payments sent once

Request keys, a single-sender claim, and no blind retries: a lost Nessie response becomes Unknown and is reconciled, never resent.

Hardened edge

scrypt passwords, hashed session tokens, exact Origin + CSRF on every change, 16 KB bodies, login rate limits and lockout.
